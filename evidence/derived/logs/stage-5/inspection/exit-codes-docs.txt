Exit codes
The commands that gate a pipeline report their verdict through the exit code. This page lists what each command returns at v0.77.2. v0.77.2 keeps the eleven-command scheme and changes ten results that its release notes list: six commands (soup distill-prompt, soup data evolve and gen-magpie, soup data filter --perplexity, soup data dedup --field, soup registry push --run-id) now stop with a non-zero code where v0.77.1 exited 0; soup eval quant-check reports an unparseable --tasks file as 3 before any model loads, soup plan and soup apply report malformed YAML or an unreadable config as 2, soup quantize reports a --to value Rich read as markup as 2, soup ship --progress jsonl exits 130 on Ctrl+C, and soup loop status exits 2 on a stored spend that is not a finite number (what v0.77.2 adds). v0.77.1 kept the eleven-command scheme and moved one code inside it, a soup eval gate suite that is not valid YAML (1 to 3); the rest of it is refusals under codes the commands already used, and soup plan and soup apply going from 0 to 1 on a config soup train refuses (what v0.77.1 adds). v0.77.0 kept the eleven-command scheme of v0.76.0 and moved none of its codes: it added new conditions under codes these commands already used, and two new uses of 3 outside the scheme (what v0.77.0 adds). v0.76.1 moved no code either: its YAML read limits refuse under codes the commands already used (what v0.76.1 adds). v0.76.0 moved eleven of them onto one scheme and changed which number means "the gate said no" on several, so a CI step written against v0.75.2 can now pass a failing gate without saying so. Read what moved before anything else.
Wherever it could be done without a model or a network service, each row was checked at v0.76.0 by running the command against a small local fixture: soup ship, soup expect, soup data validate, soup data lint, soup lock check, soup lock show, soup lock write, soup eval gate, soup eval against (its error branches), soup eval quant-check (its error and --allow-stub branches), soup eval behavior, soup eval checklist, soup eval unlearning, soup diagnose (the --evidence path), soup plan, soup apply, soup train (its config refusals), soup doctor --config, soup attest emit --sign sigstore without the extra, soup plugins install, soup ab, soup data clean and soup rewind. Rows for commands that need a model, a GPU, an adapter or a network service (a MAJOR verdict from soup eval quant-check, soup data canary check, soup draft measure, the verdict of soup shrink, soup probe, soup adapters scan, soup adapters check, soup adapters audit, soup recipes verify, soup bench train, soup can run, soup ui, the live paths of soup eval behavior and soup diagnose) were read from the call site and not run, and so were the rarer error branches elsewhere, such as the hardware-fit refusal in soup train. The rows that read a YAML config or suite (soup train, soup doctor --config, soup plan, soup apply, soup ship --config, soup eval gate --suite and the config-read branch of soup adapters audit) and the error branches of soup eval quant-check were run again on the v0.76.1 binary. Most rows that v0.77.0 changed were run on the v0.77.0 binary beside the v0.76.1 tree; the --strategy cmaes row and the judge_rank budget and Sesame CSM refusals of soup train were read from the call site. The rows that v0.77.1 changed or added were run on the v0.77.1 binary, most of them beside the v0.77.0 tree: soup eval gate with a malformed suite, soup train --gate, soup plan, soup apply, soup ship --config and --progress jsonl, soup recipes verify --config, soup data with an --output that names an input (each of the eighteen commands, with the same string or a default output name), soup adapters bisect, soup adapters check, diff, scan, merge and arithmetic with NumPy made unimportable, soup train --cloud lambda, soup profile and soup infer --backend. The one exit that was read from the call site is the --progress jsonl exit 1 on an unexpected exception, and a symbolic link or a Windows spelling of the same path was not run. The rows that v0.77.2 changed were run on the v0.77.2 binary: soup plan and soup apply (malformed YAML, a config that cannot be read, an unknown key, and a distill config with and without --minillm-on-policy), soup eval quant-check (a --tasks file with invalid JSON, with a row missing prompt and with a name that does not end in .jsonl, and a model that does not load), soup distill-prompt, soup data dedup --field, soup data filter --perplexity and --score-only without torch, soup quantize --to "[/]", soup registry push --run-id on a running, a failed and a completed run, soup loop status on a hand-edited state, and soup serve --tool-auth-token. The soup ship --progress jsonl exits 130 and 1 and the soup data evolve and gen-magpie exit 1 (which needs a provider) were read from the call site; the release notes say the 130 was not exercised by hand.
The PR gate that soup ci init writes runs soup data validate (with --min-valid-fraction 1.0 in a workflow generated by v0.77.0, so one row that does not convert fails the job; an existing workflow keeps its old step until you regenerate it with soup ci init --force), soup expect and soup ship --evidence in that order, and a non-zero exit from any step fails the job. Everything below is what those exits, and the rest, mean.
The scheme the gate commands share
soup_cli.utils.exit_codes defines four values. Eleven commands adopt the scheme as a whole, a mistyped flag included: soup ship, soup expect, soup data validate, soup data lint, soup eval gate, soup eval quant-check, soup eval against, soup eval behavior, soup eval checklist, soup lock check and soup recipes verify.
0 the check passed.
1 something broke that is not about your input: a model that would not load, an unwritable output, an unexpected exception, an unreachable judge.
2 the gate said no: a failed check, a regression, drift, DON'T SHIP, a MAJOR verdict, a failed expectation.
3 the invocation or an input is wrong: a missing or unparseable file, a bad value, an unknown flag, a schema the command rejects.
Every other command keeps its own scheme, listed in the tables below, although a few individual codes moved too (the last rows of the table above), and several of them still use 2 for a rejected argument and 3 for a failed check. Do not carry the scheme over to a sibling: soup diagnose borrowed 3 for three conditions (a NOT_RUN verdict, --attach-to-registry without --output, a bad --tokenizer) and kept 2 for the rest, and soup data doctor, soup eval unlearning and soup probe sit next to commands that moved and did not move with them.

The step that now passes silently is any test for the old number. A script that treats soup eval gate exit 1 as "the gate failed", or soup lock check exit 3 as "drift", or soup expect exit 3 as "an expectation failed", no longer matches a failing gate: it gets 2. A step written as "fail on any non-zero exit" keeps working and cannot tell the causes apart. Change the test to this:
A failed gate is 2 on every command in the scheme, soup ship included (which already used it).
3 means your invocation or input is wrong. Do not treat it as a regression, and do not swallow it: a typo in the CI file used to exit 2, which on soup ship read as DON'T SHIP, and on all eleven commands it now exits 3.
1 means something crashed.
The two files Soup generates were updated to match. The workflow from soup ci init wraps each of its three steps: exit 2 prints a step-specific message (data validation failed: unusable data, expectations suite failed: quality regression, gate rejected: model failed ship checks) and exits 2, and any other non-zero prints usage or configuration error (exit N) and exits with N. An older committed workflow still fails the job on any non-zero. The pre-push hook that soup eval gate-install writes now exits 2 on a regression and passes any other non-zero exit of soup eval against through, with [soup] pre-push gate error: configuration or usage error (exit N); before v0.76.0 it turned every non-zero exit into 1. The hook still does nothing unless SOUP_CANDIDATE_RUN_ID is set.

Four things the table does not say.
The refusal of an output that is an input is upstream's count of eighteen, and it is not every soup data command. The first five came in #2245 and the other thirteen in #2261. Each compares its outputs with its inputs before the data is read; for some commands a missing input file is still reported first (sample, dedup, filter, convert, topics, doctor, lint, canary insert, from-traces) and for the others the same-file refusal comes first, under the same exit code. Upstream lists the spellings it refuses: the same string, ./x, sub/../x, the absolute path, a case variant on a case-insensitive file system, a hard link or a symlink, and on Windows also a trailing space or dot, ::$DATA and a junction; the check behind this page used the same string and the default output names, not a link or a Windows spelling. canary insert also refuses a --manifest that is the dataset or the --output (exit 1). The commands upstream has not checked are mix, forge, generate, gen-magpie, recipe and canary check, and soup data persona-mix still writes over its --prompts file when --output names it (it exited 0 and replaced the file here). Both are tracked in #2226. (Since closed in v0.77.2: soup data ingest refuses an --output that names its source document, and soup data persona-mix, generate, canary check, mix --optimize, forge and recipe --execute refuse an --output that names one of their inputs, all before anything is read and all with exit 1; soup adapters arithmetic and merge refuse an --output that is an input adapter with exit 1 (Output path refused: ..., #2274, #2349, #2379). The shared refusal no longer starts with Error: or Plan failed:. Here persona-mix, ingest, canary check, forge and adapters merge were run and each left its input untouched; the other commands are as the release notes list them.) The v0.77.0 advice to give --output another path is now the refusal's own message: --output 'pii.jsonl' is the same file as --input 'pii.jsonl'; choose a different --output.
soup plan and soup apply print the same lines as soup train. The first line is Config validation error:, then one line per setting. A syntax error was 1 at v0.77.1 and is 2 since v0.77.2 (what v0.77.2 adds); a file over a read limit or a config that is not a mapping is still 2, a missing file is still 1. soup doctor --config stays 2 and soup recipes verify --config and soup ship --config stay 3 on the same config. One config loads under soup train only because of a flag: a distill config with training.minillm_enabled: true, training.minillm_teacher_mix_ratio: 0 and no training.minillm_on_policy loads with soup train --minillm-on-policy, but soup plan and soup apply have no such flag and exit 1, so write training.minillm_on_policy: true in the YAML (upstream listed this as a known limitation). (Since closed in v0.77.2: both commands take --minillm-on-policy, #2315.)
soup adapters bisect still exits 2 for two different things. Exit 2 is BROKEN_AT, and it is also an --eval-command whose program is not on PATH, so read the first line of the output: the second prints --eval-command program 'x' was not found on PATH; install it, put it on PATH, or give its path and no verdict panel. A program given with a directory part (./tool, an absolute path) ran as given. When {ckpt} is part of the program name, the name was resolved for each probe and a miss counted as a failed probe, as before. (Since closed in v0.77.2: a program that cannot be started exits 2 with no verdict, whether it is fixed (refused before the first probe) or completed by {ckpt} (resolved for each probe, so the refusal can come after earlier probes ran); a program given with a path that is not a file, or is not executable, exits 2 with --eval-command program './x' could not start: .... A program that starts and exits non-zero, or times out, is still a failed checkpoint. On Windows the template is split without POSIX quoting, so write "{ckpt}" in double quotes, #2314, tracked as #2488. Here a missing fixed program, a name that {ckpt} completes and a ./ path that does not exist all exited 2 with no verdict.)
Missing packages are named now, under the same code. soup adapters check, diff and scan without NumPy exit 1 with numpy package required; pip install "soup-cli[train]" (or pip install numpy); soup adapters merge and soup adapters arithmetic exit 1 with numpy and safetensors packages required; pip install "soup-cli[train]" (or pip install safetensors numpy) before they read an adapter (#2141). Through v0.77.0 check reported the missing NumPy as a corrupt weights file and diff ended in a ModuleNotFoundError traceback.
Two options are new and add little to the codes. soup ship --progress jsonl writes JSONL events to stderr and leaves stdout and the exit codes alone: 0 for SHIP, 2 for DON'T SHIP (a completed verdict ends with an end event, not an error), 3 for a usage or input error (an error event with the fixed text execution_aborted); a value other than jsonl exits 3. In that mode an unexpected exception is exit 1 with start and error events and no traceback (read from the call site; since v0.77.2 it also prints an Error: line on stdout, and Ctrl+C is 130, see what v0.77.2 adds). soup infer --backend takes transformers or mlx; any other value is Click's 2, and --backend mlx with an option MLX generation does not take, or without the [mlx] extra, exits 1 naming it (the options).

Six things the table does not say.
The old results of rows 2 to 6 are upstream's words, not a finding of this page. The v0.77.2 notes describe the old result of soup distill-prompt with no usable prompt as "empty output written" (now exit 3 with the output untouched, #2209) and that of soup data evolve and gen-magpie when no row was produced and a provider call had failed as "output emptied" (now exit 1 with the output kept, #2348; the release notes put it as "every provider call failed", the code at the tag refuses when no row survives and at least one call failed). soup data filter --perplexity and --score-only without torch or transformers exited 0 with "unfiltered or partial" output (#2377), and soup data dedup --field <key> with a key absent from every row exited 0 with "distinct rows dropped" (#2336). soup registry push --run-id on a run that was not completed exited 0 with "an entry registered" (#2248). If a script ran one of these on v0.77.1 and kept the file, look at the file. On v0.77.2 the reason is printed, among other lines, for example --field 'x' is absent from every row; choose a field present in the dataset. and No prompts found in traces: 0 of 2 trace rows had a prompt ....
soup plan and soup apply now exit 2 on a YAML syntax error, and every other code is as at v0.77.1. A config that is not valid YAML, or that cannot be read, prints one line naming the config (Config 'soup.yaml' is not valid YAML: mapping values are not allowed here (line 2, column 7), or Config 'soup.yaml' cannot be read: Permission denied; a file that is not valid UTF-8 prints Config 'soup.yaml' is not valid UTF-8: ... the same way) and exits 2. Three rules that hold for every command
0 is success. --help exits 0.
Click rejects a bad invocation with exit 2 before the command's own code runs, except on the eleven commands in the scheme, where it is 3. That covers an unknown command or flag, a missing required option, and a value that fails Click's own type check. soup ship --bogus and soup ship --forgetting-threshold abc exit 3 at v0.76.0; soup diagnose --bogus, soup data doctor --bogus, soup eval unlearning --bogus, soup adapters ..., soup lock write, soup lock show and soup train --bogus still exit 2.
An unexpected exception prints a short error and exits 1, and Ctrl+C exits 130. soup --verbose <command> shows the traceback. (A malformed YAML suite passed to soup eval gate was the example through v0.77.0, when it stayed 1 rather than 3; since v0.77.1 it exits 3 with a message naming the file.) soup train installs no Ctrl+C handler of its own at v0.77.0, so interrupting a local run is an ordinary 130 (a --cloud runpod --cloud-submit run instead keeps waiting for the controller to delete the Pod and exits with its code), see Observability.
Where one code means two things
soup diagnose: exit 2 is a MAJOR verdict, and it is also a missing --evidence file, an invalid --citation-style and a mistyped flag. Exit 3 is the new NOT_RUN verdict, and it is also --attach-to-registry without --output and a bad --tokenizer.
soup data doctor, soup eval unlearning and soup probe: exit 2 is a MAJOR verdict, and each of them also uses 2 for rejected inputs and for a mistyped flag (preference data handed to soup data doctor, a missing --evidence file).
soup shrink, soup reward stress, soup draft measure, soup adapters check, soup adapters audit: exit 2 is the verdict (DON'T SHIP, gameable, below the floor, inactive, diverged) and also what Click returns for a mistyped flag.
soup adapters scan: exit 1 is a WARN verdict and also an adapter that is missing or unreadable.
soup adapters verify and soup adapters check-safetensors: a failed check is 1 by default and 3 with --strict. Both also exit 3, with or without --strict, when the directory is outside the working directory or is a symlink, and soup adapters verify exits 3 on a .soup-signature.json that cannot be parsed.
soup adapters bisect: exit 2 is BROKEN_AT and also a rejected argument, and, since v0.77.1 for a fixed program and since v0.77.2 for any program (one that {ckpt} completes included), an --eval-command program that is not on PATH or cannot be started; the first line of the output says which.
soup adapters merge: exit 2 is a rejected argument and, with --strict-verdict, a MAJOR canary verdict; exit 3 is a refused gate, not a verdict.
soup attest verify: exit 3 is an invalid signature or a policy mismatch, 2 is an input that cannot be read, and 1 is a Sigstore verifier that is not available.
soup env check: exit 3 is ABI drift against the lock and also an installed package outside the bounds Soup declares for itself.
soup train: exit 2 can arrive after a finished run, and so can exit 3 (--diagnose-gate); a run that a gate stopped early exits 0. See the train rows below.
